# Pixel Art gallery

The shared realtime canvas stays in `Pixel_Art`, row `id = 1`. The gallery
stores immutable 16×16 color snapshots separately, six records per page.
Cards show an optional creation name above the image, with a permanent number
(`#0001`) on the left and `by username` on the right below it. The compact save
control accepts an optional name; an empty name defaults to Pixel Art. Dates
stay stored but are not displayed.
Public metadata is limited to number, username and colors; per-pixel contributor
names are not copied. The UI uses the same column orientation as the canvas.

## Sessions

This is a compatibility bridge for the existing `Users` login, not Supabase
Auth. The login RPC validates credentials server-side and returns a random UUID
session token plus profile data without a password. Tokens expire after seven
days and are revoked at logout; password changes invalidate them. The token
and credential fingerprint table has no public read/write access. Direct
writes to the gallery are denied; only `save_pixel_art` can insert after
validating the token. The RPC sets the author itself, validates the title and
256 hexadecimal colors, and serializes saves with a ten-second cooldown.

The existing Users system still stores plaintext passwords. Migrating those
accounts to Supabase Auth, adding login throttling, and securing unrelated
profile/storage operations are separate improvements; this change does not
claim to replace the site's entire authentication system.

## Chat delivery and read receipts

`20261019200000_chat_receipts.sql` was applied on 2026-10-19 after explicit
owner approval. Transactional verification passed before committing: sent,
delivered, read, recipient ownership, invalid sessions and private table
permissions. Test chats, messages and sessions were rolled back. The final
query confirmed RLS enabled and direct anon reads/updates blocked. Deploy the
updated frontend to every participating browser for receipt acknowledgements.

Receipts have RLS enabled and no direct client table privileges. The
`chat_sync_receipts` RPC validates the existing session token; it lets each
recipient acknowledge only their own receipt. It returns pending message
contents, requires a subsequent delivery ACK, and returns aggregate statuses
only for the caller's sent messages. Checks stay grey/single if unavailable.
Recipients are frozen at message creation, excluding the sender. In public
rooms this includes all registered accounts at send time. Double grey/blue
requires all recipients to confirm delivery/reading respectively. Older
messages start without inferred delivery/read times.

The chat page receives pending messages across its rooms while open. Reading
requires the message to intersect the visible conversation viewport while the
page is visible and the window has focus. Receipts synchronize every three
seconds and on focus/visibility/reconnection. They do not work after the
website is closed; there is no background push service. Older deployed
clients cannot acknowledge receipts until updated. SQL rollback verification
passed in Supabase before the migration was committed.

Local isolated browser checks verified single grey, double grey, double blue,
reception ACK after receiving contents, no read ACK before opening a room,
and aligned account/composer separators. Build and existing unit tests pass.

## Permanent personal deletion

`20261019230000_chat_permanent_deletion.sql` replaces the recoverable delete
behavior. Confirmed Delete forever calls `chat_delete_forever`; Deleted chats
and Restore chat are removed from the UI. The private per-user tombstone keeps
the room out of the account's lists permanently. Other participants' shared
history remains. This is not a physical purge of shared Messages records.
The server rejects restoration and archiving of a deleted room through both
current and legacy RPCs. Archive/unarchive remains reversible. Old clients must
update before deleting; their previous delete RPC now rejects the operation.

The migration was applied on 2026-10-19 after transactional tests verified
permanent deletion, blocked restoration including the legacy RPC, session and
membership checks, and isolation. No real deleted records existed when applied;
the migration refuses to convert existing recoverable deletions silently. Browser
QA used local fixtures to verify Cancel, Delete forever and persistence across
reload without a recovery list. The app asks the user to confirm each deletion.
